# 一、这个项目是什么

你将要构建的是一款**浏览器内运行的像素风殖民地模拟经营游戏**，名为《星尘殖民地》（Stardust Colony）。

它的灵魂来自开罗游戏（Kairosoft）的《宇宙探险物语》——轻松、温暖、正反馈驱动、看小人跑来跑去就很开心。但它在三个方向上做了关键扩展：

1. **六维引力系统**取代了传统的简单分类标签，让所有建筑、产品、居民、游客、区域都在一个统一的六维向量空间中可计算——这意味着"什么东西吸引什么人"不再是硬编码的对照表，而是一个可以自然涌现出无限组合的数学系统。

2. **AI动态内容生成**取代了固定的文本库——建筑组合效果、产品描述、游客性格与对话、探索事件、居民日记、年终评比，全部由AI根据当前游戏状态实时生成。但AI不是主角——它是调味料。游戏的核心数值系统完全在前端本地运行，即使AI完全不可用，游戏也能正常玩，只是少了个性化文本。

3. **完整的多级工业产线**让"种田→加工→消费"的经济循环有了真正的深度——玩家不只是建一个农田就完事，而是要思考小麦→面粉→面包→餐厅→游客消费这条完整的价值链。

# 二、设计目的

## 2.1 为什么做这个

制作者（观心）长期创作的是高压力、强博弈、文明尺度决策的SillyTavern角色卡。那些卡片要求玩家持续进行沉重的道德抉择和政治权衡。这个项目是**刻意反向的调剂品**——它的存在目的就是让人放松。

不是那种"空洞的放松"，而是**有深度的放松**——系统足够深，让喜欢优化和规划的人可以投入几十个小时追求完美布局；但同时绝对不会因为"做错了选择"而受到惩罚。唯一的压力来自"我想让我的殖民地更好"，而不是"如果我做错了世界会毁灭"。

## 2.2 核心情感目标

这款游戏要让玩家在以下时刻感到快乐：

| 时刻 | 快乐的来源 | 设计如何支撑它 |
|------|-----------|---------------|
| 看到居民小人在建筑之间跑来跑去 | 世界在自主运转的安心感 | 居民状态机驱动自主行为 |
| 建筑放下去的瞬间触发了一个意想不到的组合 | 发现的惊喜 | AI组合判定，无限可能性 |
| 看到产品品质从B逐渐提升到A+再到S | 缓慢但确定的成长 | 品质系统关联工人成长、设施等级、组合加成 |
| 章鱼星人吃了星糖吐司之后八条触手都在抖 | 被逗笑 | AI生成的个性化游客反应 |
| 切换引力热力图，看到自己精心规划的美食街区一片温暖的橙色 | 规划成果的视觉化 | 六维引力场实时渲染 |
| 读汉克的日记，发现他又在嘴硬 | 对虚拟角色产生感情 | AI日记系统 + 性格标签一致性 |
| 面包工坊冒出的烟、喷泉的水花、花田的蝴蝶 | 世界的质感和细节 | 微小但持续的视觉反馈 |
| 年终评比排名从#1200上升到#400 | 长线进步的确认 | 年度结算系统 |

## 2.3 反目标——这个游戏绝对不要的东西

| 坚决避免 | 原因 |
|---------|------|
| 角色永久死亡 | 这是一个让人放松的游戏。战斗失败=被抬回家休息几天。绝不死人 |
| 不可逆的灾难 | 没有火灾烧毁建筑、没有外星入侵摧毁殖民地、没有经济崩溃。最坏情况=发展速度变慢 |
| 道德困境 | 不会让玩家在"救这个人还是救那个人"之间选择。所有选择都是"哪个更好"而不是"哪个没那么坏" |
| 黑暗剧情/恐怖元素 | 连暗示都不要。怪物是自然生态的一部分，外星人是友善的（最多有点奇怪） |
| 强制时间压力 | 没有倒计时、没有"必须在N天内完成否则失败"。年终评比只决定排名升多少，不会因为考得差而扣分 |
| 过于复杂的操作 | 玩家的核心操作就是：选一个建筑→点一个格子→放下去。不需要微操单位、不需要手动控制战斗（自动进行） |
| Pay-to-win或变相强制消费 | 这是一个单机离线游戏，唯一的运行成本是AI API调用，且AI不可用时游戏仍然完整可玩 |

# 三、设计目标

## 3.1 最小可玩原型（MVP）

第一个可以"玩起来"的版本需要包含：


✅ 网格地图渲染（12×10 初始区域）
✅ 6种基础地形（平原、森林、水域、山地、岩地、沃土）
✅ 建筑放置/拆除
✅ 道路系统（建筑必须连接到指挥部）
✅ 5个初始建筑（帐篷、麦田、伐木场、面包工坊、仓库）
✅ 3个初始居民（有名字、有属性、有状态机）
✅ 基础生产循环（小麦→面包）
✅ 资源管理（金币、食物、木材、石材）
✅ 时间系统（日/季/年 + 速度控制）
✅ 存档/读档


MVP 不需要 AI——所有内容都是前端硬编码的。先确保数值系统和游戏循环正确运转。

## 3.2 第二里程碑：引力系统


✅ 六维引力标注（所有建筑和地形都有引力向量）
✅ 引力场计算（每格地块的总引力 = 周围建筑贡献的叠加）
✅ 引力热力图（6种颜色叠加层可切换查看）
✅ 居民空闲行为受引力偏好驱动


## 3.3 第三里程碑：游客系统


✅ 宇宙港建筑
✅ 4个预设外星种族（章鱼星人、水晶星人、机甲族、花灵族）
✅ 游客到访逻辑（频率受好感度影响）
✅ 游客路径由引力匹配度决定
✅ 游客消费 → 金币收入 + 好感度增长
✅ 好感度阈值奖励（30/60/100）
✅ 个体游客的偏好波动（见下方3.5节）


## 3.4 第四里程碑：AI接入


✅ AI请求队列（优先级排序、并发控制、缓存、降级）
✅ 组合判定（建筑放置后检查）
✅ 产品描述生成
✅ 游客个性和对话生成
✅ 居民日记生成
✅ 探索事件生成
✅ 年终评比生成


## 3.5 个体游客的动态偏好波动

**这是一个关键设计细节：同一种族的不同个体应该有微小但有意义的偏好差异。**

原理：每个外星种族有一个**基础偏好向量**（species-level），但当AI生成具体的游客个体时，在每个维度上施加 ±15% 的随机波动。这样：

- 大多数章鱼星人仍然最爱美食（基础food=90），但偶尔会有一只章鱼对文化特别感兴趣（波动后culture从40变成52）
- 这个波动足够小，不会破坏种族特征（章鱼还是爱吃的），但足够大，让每一批游客的行为路径有微妙差异
- 玩家会注意到"咦，这批章鱼怎么去了图书馆？"——这种微小的意外是乐趣的来源

实现方式：


function generateIndividualPreference(speciesBasePreference) {
  const individual = {};
  for (const [dim, baseValue] of Object.entries(speciesBasePreference)) {
    // ±15% 波动，使用正态分布（而非均匀分布）使极端值更稀有
    const variance = baseValue * 0.15;
    const offset = gaussianRandom() * variance; // 均值0，标准差=variance
    individual[dim] = Math.max(0, Math.min(100, Math.round(baseValue + offset)));
  }
  return individual;
}

// 高斯随机（Box-Muller 变换）
function gaussianRandom() {
  let u = 0, v = 0;
  while (u === 0) u = Math.random();
  while (v === 0) v = Math.random();
  return Math.sqrt(-2.0 * Math.log(u)) * Math.cos(2.0 * Math.PI * v);
}


当AI生成游客团时，前端先用这个函数算出每个个体的偏好向量，传给AI作为上下文——AI基于这些波动后的数值来生成对应的性格描述和行为逻辑。这样数值和叙事是一致的：


// 传给AI的个体数据示例
{
  "individual_id": "tourist_squid_047",
  "species": "squid_aliens",
  "species_name": "章鱼星人",
  "base_preference": { "food":90, "knowledge":20, "comfort":60, "adventure":10, "culture":40, "nature":30 },
  "individual_preference": { "food":82, "knowledge":24, "comfort":55, "adventure":12, "culture":52, "nature":33 },
  // AI看到这个个体的culture异常高（52 vs 基础40），可以生成：
  // "这只章鱼穿着一件印有古典油画的T恤。它说这是'跨文明美学研究'的一部分。
  //  但你注意到它在特产店里盯着水晶雕塑看了很久，触手不自觉地伸了出去。"
  "budget": 3200,
  "personality_seed": ["foodie", "art_lover"]  // 性格标签也可以基于波动方向生成
}


**性格标签的动态生成规则：**

当某个维度的个体偏好相对于种族基础偏好偏移超过 ±10% 时，可以为该个体附加一个额外的性格标签：


function generatePersonalityTags(speciesBase, individual, speciesPersonalityPool) {
  // 从种族性格池中随机选1-2个基础标签
  const tags = pickRandom(speciesPersonalityPool, randomInRange(1, 2));
  
  // 检测偏移维度，附加特殊标签
  const DRIFT_THRESHOLD = 0.10; // 10%偏移
  const DRIFT_TAGS = {
    food:      { high: 'glutton',         low: 'picky_eater' },
    knowledge: { high: 'bookworm',        low: 'anti_intellectual' },
    comfort:   { high: 'luxury_seeker',   low: 'spartan' },
    adventure: { high: 'thrill_seeker',   low: 'cautious' },
    culture:   { high: 'art_lover',       low: 'philistine' },
    nature:    { high: 'nature_lover',    low: 'urbanite' }
  };

  for (const dim of Object.keys(speciesBase)) {
    const base = speciesBase[dim];
    const ind = individual[dim];
    const drift = (ind - base) / Math.max(base, 1);
    
    if (drift > DRIFT_THRESHOLD && DRIFT_TAGS[dim]) {
      tags.push(DRIFT_TAGS[dim].high);
    } else if (drift < -DRIFT_THRESHOLD && DRIFT_TAGS[dim]) {
      tags.push(DRIFT_TAGS[dim].low);
    }
  }

  return tags;
}


这套机制确保了：
- **种族特征是稳定的**：100只章鱼星人的平均偏好向量仍然是 food=90, knowledge=20 
- **个体是有趣的**：每一只章鱼都有微妙的个人差异，AI可以把这些差异变成有画面感的叙事
- **玩家可以感知**：偶尔出现的"异常"游客（比如一只特别爱冒险的章鱼）会成为玩家的谈资
- **计算是确定的**：偏好波动在前端完成，不依赖AI，确保经济系统的可预测性

# 四、核心设计原则

## 4.1 开罗法则：你永远不会输

这条法则贯穿整个游戏的每一个系统设计：

- **不存在"Game Over"**。玩家不会破产（金币最低为0，但不会产生负债）。居民不会永久死亡。建筑不会被摧毁。
- **犯错的代价是"发展慢了一点"，而不是"失去了什么"**。建错了建筑？拆掉退回50%资源。工人分配不合理？随时重新调配。科技点错了方向？科技是并行共存的，不存在"点错了就浪费了"。
- **每一个操作都有正反馈**。放下一个建筑→看到它出现在地图上→工人开始往那里走→产品开始产出→金币开始增加→可以放下更多建筑。这个正循环永远不会断裂。

这不意味着游戏没有深度。深度来自**优化空间**——同样的资源投入，精心规划的玩家可以获得比随意放置高3-5倍的产出效率。但即使是最随意的玩家也能做到"慢慢变好"。

## 4.2 AI是调味料，不是主菜

**前端的确定性系统必须能够独立运行。** 如果AI宕机了、API额度用完了、网络断了，游戏仍然可以正常玩。具体来说：

| 系统 | AI可用时 | AI不可用时 |
|------|---------|-----------|
| 组合判定 | AI根据标签推理生成新组合 | 回退到预编码的30个基础组合表 |
| 产品描述 | AI生成个性化名称和描述 | 显示默认名称+"品质X级"，无描述 |
| 游客个性 | AI生成独特的名字、台词、行为 | 从20个预设模板中随机选取 |
| 探索事件 | AI生成完整的叙事和选项 | 从50个预设事件中按难度随机抽取 |
| 居民日记 | AI生成个性化的第一人称日记 | 不显示日记（或从通用库中选一条） |
| 年终评比 | AI生成详细评语和幽默点评 | 纯数值报告，无文字评语 |

实现这一点的关键是：**AI生成的所有内容都是"附加在数值上的装饰"，而不是"决定数值的来源"。** 品质等级由前端的数学公式决定，AI只是给这个品质等级写一段好看的描述。游客去哪里消费由引力匹配度公式决定，AI只是给这个决定配上一句好笑的台词。

## 4.3 六维引力是万有语言

游戏中的每一个新实体——无论是前端预设的还是AI动态生成的——都必须携带一个六维引力向量。这是它与整个经济系统交互的唯一接口。

**为什么这很重要：** 如果AI生成了一个新建筑"水晶音乐厅"，前端不需要理解"水晶音乐厅"是什么——它只需要读取这个建筑的引力向量 `{ food:0, knowledge:30, comfort:45, adventure:5, culture:80, nature:15 }`，然后像处理任何其他建筑一样把它纳入引力场计算。游客会根据自己的偏好决定要不要去，居民会根据自己的亲和力决定喜不喜欢在旁边工作——全部自动完成，无需为新内容写额外的逻辑。

**这就是为什么每一个AI输出的Schema都要求包含引力向量。** 它不是可选字段。它是新内容融入世界的通行证。

## 4.4 数值透明，组合隐藏

借鉴开罗的经典设计哲学：

- **数值透明**：每个建筑的引力值、生产效率、消耗成本——全部明文显示给玩家。不存在"隐藏属性"。玩家可以精确计算"如果我在这里建一个面包工坊，它的美食引力会覆盖到哪些格子"。
- **组合隐藏**：哪些建筑放在一起会触发组合——这需要玩家自己实验。游戏不会给你一个完整的组合列表让你照着拼。你看到面包工坊的提示"旁边有牧场的话也许能做更好的面包"，然后你试着把牧场挪过来——触发了一个你没见过的组合——这就是"发现的惊喜"。

AI让这种惊喜变成了**几乎无限的**——因为AI可以根据标签的逻辑关联推理出预设表里没有的组合。玩家不可能穷举所有可能性。这让每一次实验都有可能发现新东西。

## 4.5 时间是朋友，不是敌人

不存在"必须在N天内完成"的任务。不存在"如果年末评分不够就会被淘汰"的惩罚。时间只做两件事：

1. **让你的东西变多**（资源积累、居民成长、科技推进）
2. **给你一个节奏感**（季节变化影响农业产出和游客类型、年终评比提供一个期待和回顾的节点）

玩家可以在第1年春天暂停游戏，盯着地图看半小时规划布局，然后开始建设。这半小时不会浪费任何游戏内资源——时间被暂停了。

## 5.2 关键设计决策

### 单一状态对象

整个游戏状态存储在一个 `gameState` 对象中。所有系统通过直接读写这个对象来交互。不使用复杂的状态管理框架——这个游戏的状态结构虽然大，但数据流向是单向且可预测的（时间推进 → 系统更新 → 状态变化 → 渲染反映）。

### 事件总线

用一个简单的 EventEmitter 模式来解耦模块间的通知。例如：

- 建筑放置 → 发出 `building_placed` 事件 → 引力场重算 + 组合检查 + UI更新
- 产品完成 → 发出 `product_completed` 事件 → 底部通知栏 + AI描述请求 + 统计更新
- 游客到达 → 发出 `tourist_arrived` 事件 → 飞船降落动画 + AI个性生成

这避免了模块之间的直接调用依赖。

### 渲染与逻辑分离

Canvas只负责把 `gameState` 的当前快照画出来。它不修改任何状态。所有状态修改都在逻辑层（主循环中的各个系统更新函数）完成。这使得：

- 暂停时可以继续渲染（交互查看信息），但逻辑不推进
- 加速时逻辑可以一帧处理多个tick，渲染仍然只画最终结果
- 未来如果需要回放或调试，可以通过重放状态序列实现

# 六、AI接入的哲学

## 6.1 何时该调AI，何时不该

**该调AI的场景：**
- 需要**创造性文本**的地方（描述、对话、评语、事件叙事）
- 需要**基于逻辑推理做开放性判断**的地方（组合效果判定——"这些建筑放在一起合不合理？"）
- 需要**生成新内容模板**的地方（新科技、新建筑、新种族——它们的引力向量和数值由AI提议，前端验证并约束到合理区间）

**不该调AI的场景：**
- 任何**纯数值计算**（品质计算、引力场叠加、消费金额、路径选择——全部在前端用公式完成）
- 任何**需要即时响应**的交互（放建筑、调整工人、打开面板——这些必须零延迟）
- 任何**涉及游戏核心规则**的判定（是否能建造、资源是否够、是否满足前置条件——这些由前端硬编码的规则引擎决定，不交给AI）

## 6.2 AI输出的验证

前端必须对AI的每一个输出做验证。AI很聪明，但它可能犯蠢：


function validateAIOutput(output, schemaType) {
  const validators = {
    combo_check: (o) => {
      if (typeof o.combo_detected !== 'boolean') return false;
      if (o.combo_detected) {
        if (!o.combo?.id || !o.combo?.name) return false;
        if (o.combo.tier < 1 || o.combo.tier > 3) return false;
        // 数值区间检查
        for (const bonus of o.combo.bonuses || []) {
          const val = parseInt(bonus.value);
          if (o.combo.tier === 1 && (val < 5 || val > 15)) return false;
          if (o.combo.tier === 2 && (val < 15 || val > 35)) return false;
          if (o.combo.tier === 3 && (val < 30 || val > 50)) return false;
        }
        // 引力加成总和检查
        const gravSum = Object.values(o.combo.gravity_bonus || {}).reduce((s,v) => s + v, 0);
        if (o.combo.tier === 1 && gravSum > 10) return false;
        if (o.combo.tier === 2 && gravSum > 20) return false;
        if (o.combo.tier === 3 && gravSum > 30) return false;
      }
      return true;
    },
    product_description: (o) => {
      if (!o.name || !o.description) return false;
      if (o.quality_tier && !['D','C','B','A','A+','S'].includes(o.quality_tier)) return false;
      return true;
    },
    tourist_generation: (o) => {
      if (!o.tourist_group?.species) return false;
      if (!o.tourist_group?.leader?.name) return false;
      // 检查预算不超过种族上限的2倍
      // 检查性格标签不为空
      return true;
    },
    // ... 其他类型的验证器
  };

  return validators[schemaType]?.(output) ?? false;
}


如果验证失败：
1. 第一次失败 → 自动重试一次（不同的temperature）
2. 第二次失败 → 使用降级数据（预设的fallback）
3. 记录失败日志（帮助后续优化提示词）

## 6.3 请求节流

AI API不是免费的，也不是瞬时的。必须做好节流：

- **全局限流**：同一时刻最多2个并发请求
- **同类限流**：同类型请求最小间隔（如 combo_check 同一位置5秒内不重复）
- **优先级队列**：探索事件（玩家正在等）> 组合判定（影响布局决策）> 游客生成 > 产品描述 > 日记（纯装饰）
- **批处理**：如果1秒内有3个产品同时完成，打包成一个请求而不是发3个
- **缓存**：同样的建筑组合 → 同样的组合结果。缓存键设计见技术文档中的请求队列部分

# 七、视觉与氛围指引

## 7.1 像素画风格

- **分辨率**：16×16 或 32×32 像素的精灵图（sprite）
- **色彩**：饱和度中等偏高、偏暖色调。整体明亮，像阳光充足的午后
- **建筑风格**：圆润、可爱、微微卡通。不要尖锐的线条或威胁性的外观
- **居民小人**：大头小身（头身比约1:1.2），简单但能区分不同角色的颜色和特征
- **动画**：
  - 居民走路：4帧循环
  - 建筑运作：烟囱冒烟、水车转动、花朵摇摆
  - 产品完成：小星星/小光圈特效
  - 金币获得："+10G"飘字上升后消失

**初期实现**：可以先用纯色方块和简单几何形状代替精灵图。核心逻辑跑通后再逐步替换为像素画。MVP阶段的视觉目标是"能看清是什么"，不是"好看"。

## 7.2 音效（可后期添加）

- 放置建筑：轻柔的"咚"声
- 产品完成：清脆的"叮"声
- 金币收入：硬币声（可累积——连续收入时频率加快）
- 游客到来：飞船引擎的低沉嗡鸣 → 着陆声
- 组合触发：悦耳的和弦上升
- BGM：轻快的电子/原声混合，循环播放不疲惫

MVP可以完全没有音效。静音状态下游戏必须仍然完整可玩。

## 7.3 文字语调

所有游戏内文字——无论是预设的还是AI生成的——都应该遵循以下语调：

| ✅ 要的 | ❌ 不要的 |
|---------|---------|
| 温暖 | 冷酷 |
| 幽默但不刻薄 | 嘲讽或挖苦 |
| 简短（1-3句话） | 长篇大论 |
| 有画面感 | 抽象描述 |
| 第三人称旁白感 | 教导或说教 |
| 偶尔的吐槽 | 持续的负面评价 |

**好的例子：**
> "汉克烤的面包有一种说不上来的固执的香气。也许那就是'一丝不苟'的味道。"

> "章鱼星人墨墨用第三条触手举起了一个分数牌——但它举的是上下颠倒的。8.9分……还是6.8分？"

> "冶炼厂第一次出铁的那个下午，所有人都跑去看了。铁水的颜色比日落还亮。"

**坏的例子：**
> "玩家成功建造了设施。建筑效果已生效。" ← 太机械
> "汉克对自己的面包非常自豪。这意味着他的工作态度很积极。" ← 太说教
> "又一个无聊的一天在这个破殖民地。" ← 太消极
